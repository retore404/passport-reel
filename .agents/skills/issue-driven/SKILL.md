# Issue駆動開発

既存のGitHub issueを正として、調査からPull Request作成までを順番に完了させる。

## ワークフロー

1. リポジトリの指示を確認する。
   - 対象プロジェクトが指定する開発指示を読む。
   - 実装領域に必須のskillがあれば、計画時と実装開始時に発動する。
   - 作業ツリーの既存変更を確認し、issue対応と無関係な変更を含めない。

2. issueを取得する。
   - issue番号またはURLが不明ならユーザーに確認する。
   - 最初に `gh auth status` を実行する。サンドボックス内で失敗し、権限昇格したコマンド実行が利用できる場合は、未認証と判定する前に権限昇格して `gh auth status` を再実行する。権限昇格後も未認証なら対話ログインを試みず、ユーザーに `gh auth login` の実行を依頼して停止する。
   - `gh issue view` で番号、タイトル、本文、ラベル、URLを取得する。
   - `gh repo view` でdefaultブランチを取得する。
   - issueの期待結果、完了条件、制約、不明点を整理する。UIリソースの削除では公開入口と残る画面への依存を調べ、残る画面の表示・操作・文言に設計判断があるか確認する。実装方針を変える不明点だけをユーザーに確認する。

3. 新設または残る画面の表示・操作・文言に設計判断がある場合は、HTMLモックの承認を得る。
   - `ui-mock-design` を発動する。
   - `.agents/workspace/<Issue番号>/` に、変更対象、影響する主要状態、対象表示幅を網羅した自己完結HTMLを作成する。
   - モックと確認対象をユーザーへ提示し、フィードバックを反映したモックへの明示承認を得る。
   - 承認済みモックを実装と検証のUI契約として、Pull Request作成まで参照できる状態で保持する。

4. 実装計画を作る。
   - コードベースを調査し、現在の責務、実際の呼び出し元、変更対象、関連するテスト・Storybook・ドキュメント・公開エントリポイントを特定する。
   - 承認済みHTMLモックがある場合は、そのファイルと承認された表示状態・表示幅を実装前提に含める。
   - 実装手順、テスト方針、品質ゲート、フロントエンド変更時のVRT確認を含む計画を提示する。
   - ユーザーの明示承認を得るまで実装を開始しない。修正指示を受けたら計画を更新し、再承認を得る。

5. `main` から作業ブランチを作成する。
   - 実装前に作業ツリーを確認する。未コミット変更があれば勝手に退避・削除せず、ユーザーに整理方法を確認する。
   - `main` を最新化し、必ず `main` を起点にissue専用ブランチを作成する。再開時に対象ブランチが既に存在する場合は、`main` 起点であることとissue外のコミットを含まないことを確認して再利用する。
   - issueの内容を簡潔に表す短いタイトルを、英小文字・数字・ハイフンのslugにする。
   - ラベルを次の順に判定し、最初に一致したprefixを使う。
     1. `bug`: `fix/<短いタイトル>`
     2. `dev`: `dev/<短いタイトル>`
     3. `chore`: `chore/<短いタイトル>`
     4. `design`: `design/<短いタイトル>`
     5. いずれにも該当しない: `feature/<短いタイトル>`

6. 承認済み計画を実装する。
   - 作成したissue専用ブランチ上でのみ編集する。
   - リポジトリの開発・テストskillとTDD規約に従う。
   - issueの範囲に必要な変更だけを行い、関連成果物を更新・削除・理由付き維持のいずれかにする。

7. 品質ゲートを通す。
   - 対象プロジェクトが指定する品質ゲートを実行する。
   - 失敗した場合は原因を修正して再実行する。issueと無関係な環境要因で完走できない場合は、コミットへ進まずユーザーへ報告する。

8. 画面変更時は対象プロジェクトが指定する視覚確認を行う。
   - プロジェクト指定のVRT等の確認コマンドを実行する。
   - 承認済みHTMLモックがある場合は、対象状態・表示幅の確認基準として使用する。
   - 差分がなければ次へ進む。
   - 差分がある場合は、diff画像をユーザーに提示して判断を求め、承認を得るまでベースラインを更新しない。
   - 承認後にリポジトリ指定の更新コマンドでベースラインを更新し、VRTを再実行して成功を確認する。
   - 却下された場合は実装を修正し、品質ゲートとVRTを再実行する。

9. 変更をコミットする。
   - staged・unstaged・untrackedの最終差分を確認する。issue外の変更がstageされていればコミットせず、ユーザーに確認する。
   - issue対応の変更だけをstageする。
   - issueに `bug` ラベルがあれば、他のラベルの有無にかかわらず `fix #<issue番号>: <issueタイトル>` を使う。
   - `bug` ラベルがなければ `close #<issue番号>: <issueタイトル>` を使う。
   - issueタイトルは取得した文字列をそのまま使う。

10. pushしてPull Requestを作成し、一時モックを削除する。
   - 現在のブランチをremoteへpushする。
   - 取得済みのdefaultブランチをbaseに指定する。
   - defaultブランチとの差分が1コミットなら、PRタイトルをコミットメッセージと同じにする。複数コミットなら、対応内容を簡潔に要約したタイトルにする。
   - PR本文には、対応内容、実装・修正の簡単な説明、実行した品質確認を簡潔に記載し、issueを関連付ける。
   - `gh pr list --head <現在のブランチ> --state open` で既存PRを確認する。既存PRがあれば重複作成せず、そのPRを更新対象としてURLを報告する。
   - `gh pr create` の結果を確認し、PR URLをユーザーへ報告する。
   - `.agents/workspace/<Issue番号>/` がある場合は削除し、削除完了を確認する。

## 完了条件

- issueの完了条件を満たしている。
- 新設または残る画面の表示・操作・文言に設計判断がある場合は、実装計画の提示前にHTMLモックが明示承認されている。
- `main` 起点の正しい命名のissue専用ブランチで作業している。
- 必須の品質ゲートとプロジェクト指定の視覚確認が成功している。
- issue対応だけを含むコミットがpushされている。
- defaultブランチ向けPull Requestが作成されている。
- 対象の一時モックディレクトリが削除されている。
- 最終報告にコミット、検証結果、PR URLを記載している。
