# 新規Issue作成

ユーザーの依頼を、実行可能で検証可能なGitHub issueに変換する。

## 成果物と権限境界

- このskillが扱う成果物は、合意済みの新規GitHub issue一件と既存ラベルの付与である。
- 調査中の作業ツリーは読み取り専用で扱う。ユーザーが述べた変更要求はissueの対象として整理する。
- 実装も明示的に依頼された場合は、issue作成の完了後に別の作業として開始する。

## ワークフロー

1. 対象プロジェクトが指定する開発指示を読み、issueを管理するリポジトリを特定する。作業ツリーと関連実装から確認できる事実を調査する。
2. 最初のGitHub操作前に [GitHub Issue作成手順](references/github-issue-workflow.md) を読み、認証、リポジトリ、issue template、既存ラベル、重複issueを確認する。必須の各結果を取得した後にヒアリングへ進む。
3. 「ヒアリングスキルの選択」に従ってskillを発動し、一度に一問ずつ質問する。背景、前提、ユーザーの意向、観測可能な完了条件を明確にする。環境から確認できる事実は調査する。
4. 合意内容を、簡潔明瞭なタイトル、既存templateの見出しに沿った本文、内容分類ラベル、機能分類ラベルとして提示する。ユーザーから共有理解の確認を得る。
5. 合意済みの内容でissueを一件だけ作成し、ラベルを付与する。
6. issueのタイトル、本文、ラベルを再取得して検証する。issue URLと付与ラベルを報告する。

## ヒアリングスキルの選択

- 通常の要件整理には `grilling` skillを発動する。開発環境・CI・雑務の見直しや、用語が確定している機能変更が該当する。
- プロジェクト固有の用語の定義、概念間の関係・境界を検討する場合は `grill-with-docs` skillを発動する。ヒアリング中にこれらの論点が生じた場合も、その時点で切り替える。
- `grill-with-docs`を使う場合、語彙の保存はそのskillが要求する`domain-modeling`に従う。
- 選択したskillが利用できない場合は、利用可能な任意の手段で一問一答のヒアリングと共有理解の確認を行う。

## 中断と再開

- 通常サンドボックス内の `gh auth status` 失敗だけでは未認証と判定しない。[GitHub Issue作成手順](references/github-issue-workflow.md) に従って権限昇格で再実行し、昇格後も認証を確認できなければ、`gh auth login` の実行をユーザーに依頼して認証後に再開する。
- template、必須ラベル、完了条件について結果を変える不明点が残る場合は、選択したヒアリングスキルの一問一答へ戻る。

## 完了条件

- issue本文がリポジトリの既存templateに準拠している。
- 内容分類と必要な機能分類の既存ラベルが付与されている。
- 作成したissue URLをユーザーへ報告している。
