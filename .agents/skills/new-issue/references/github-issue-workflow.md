# GitHub Issue作成手順

## 事前確認

次の順で現在の設定を取得する。複数のコマンドをまとめた実行が途中で終了した場合、後続の未実行コマンドを確認済みとして扱わない。各項目の結果が揃うまで、ヒアリングやWeb検索による代替へ進まない。

1. `gh auth status` でGitHub CLIの認証を確認する。通常サンドボックス内で失敗した場合は、`token is invalid` などの出力だけで未認証と判定または通知せず、権限昇格したコマンド実行が利用できれば直ちに権限昇格して再実行する。権限昇格後も認証を確認できない場合にだけ、ユーザーへ `gh auth login` の実行を依頼して停止する。
2. `gh repo view --json nameWithOwner,url` で対象リポジトリを確認する。
3. ルートの `AGENTS.md` からissueを管理するリポジトリを確認する。
4. `.github/ISSUE_TEMPLATE` 配下のtemplateをすべて読み、依頼に対応するtemplateを選ぶ。
5. `gh label list --limit 200 --json name,description` で利用可能なラベルを取得する。
6. `gh issue list --state all --limit 100 --search "<主要語句>"` で同じ目的のissueがないことを確認する。候補があれば、新規作成か既存issueの利用かをユーザーに確認する。

## 本文とタイトル

- タイトルには達成する変更または解消する問題を簡潔に書く。
- 本文では選択したtemplateの見出しと順序を維持し、コメントとplaceholderを合意済みの内容に置き換える。
- 不具合にはbug templateを使う。それ以外は依頼の目的に最も近い既存templateを使う。候補を一意に選べない場合は [ヒアリングスキルの選択](../SKILL.md#ヒアリングスキルの選択)に従って確認する。
- 完了条件には第三者が観測できる期待状態を書く。
- 本文は合意した変更対象（What）、背景と目的（Why / For What）、第三者が観測できる完了状態に絞る。技術名・ツール名・ファイル名・skill 名は、それ自体が合意した変更対象または外部契約の場合に記載する。
- 調査で得た実装手順、skill の発動、使用コマンド、検証方法、影響確認の対象一覧は実装時の計画で扱う。起票前に、本文の各記述が変更対象・背景と目的・完了状態のどれに当たるか確認する。
- 現在の契約を肯定形で記述し、issue検討中の却下案や会話履歴を本文へ残さない。

## ラベルの二軸分類

実在するラベルを使用し、内容分類を一つ、該当する機能分類をすべて付与する。

### 内容分類

主目的を次の許可済み集合から一つ選ぶ。複数に見える場合は、issueの完了条件を最も直接表す分類を [ヒアリングスキルの選択](../SKILL.md#ヒアリングスキルの選択)に従って合意する。

- `bug`: 期待される挙動を満たさない不具合を修正する。
- `design`: デザインガイドライン、デザイントークン、共通デザイン規約を変更または適用する。
- `dev`: 開発環境、CI、開発ツール、開発者向けワークフローを変更する。
- `chore`: 他の内容分類に属さない雑務を行う。
- `enhancement`: 上記以外の機能または使い勝手を改善する。

### 機能分類

- 特定機能に限定される場合は、既存の `feature:<機能名>` ラベルを付与する。
- 複数機能が対象なら、対応する `feature:*` ラベルをすべて付与する。
- 機能に依存しない横断タスクには、機能分類ラベルを付与しない。
- 必要な機能ラベルが存在しなければ、ラベル作成を作業範囲に含めるかユーザーに確認する。

## Issue作成

合意済み本文を `/tmp` 配下の一時ファイルへ用意し、選択した各ラベルを明示して作成する。

```bash
gh issue create \
  --title "<title>" \
  --body-file "<body-file>" \
  --label "<content-label>" \
  --label "<feature-label>"
```

機能分類を付与しない場合は、最後の `--label` を省く。複数の機能分類を付与する場合は、各ラベルについて `--label` を繰り返す。コマンドが返したissue URLを以後の操作で再利用し、作成コマンドを再実行しない。

## 検証

- `gh issue view <issue-url> --json url,title,body,labels` でissue内容とラベルを照合する。
- 検証結果が対象issue一件で、`url`、`title`、`body`、`labels` が合意内容と一致することを照合する。
